# Hexlet Chat

[![Actions Status](https://github.com/iibadreeva/middle-frontend-project-12/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/iibadreeva/middle-frontend-project-12/actions)

Учебный frontend-проект чата в стиле Slack / Hexlet Chat.
Приложение написано на `React` и `Vite`, использует `JWT`-авторизацию, `Redux Toolkit` для состояния, `Axios` для HTTP-запросов, `Socket.IO` для realtime-синхронизации сообщений и каналов, `i18next`/`react-i18next` для интернационализации интерфейса, `react-toastify` для всплывающих уведомлений и `Rollbar` для мониторинга клиентских ошибок в production.

## Возможности

Сейчас в проекте реализовано:

- вход по логину и паролю;
- регистрация нового пользователя через страницу `/signup`;
- logout из верхнего navbar;
- сохранение сессии в `localStorage`;
- защита маршрута `/` для неавторизованных пользователей;
- интернационализация всех текстов интерфейса через i18n;
- дефолтная локаль `ru` без автоматического определения языка пользователя;
- дополнительный словарь `en` для интерфейса;
- загрузка каналов и сообщений после авторизации;
- выбор активного канала;
- создание нового канала через модальное окно;
- переименование и удаление созданных каналов через выпадающее меню;
- валидация имени канала: уникальность, длина от 3 до 20 символов и автоматическая очистка нецензурных слов;
- автоматическое переключение в только что созданный канал;
- отправка сообщений в чат с автоматической фильтрацией нецензурных слов;
- получение новых сообщений и синхронизация изменений каналов через `Socket.IO`;
- автоматическое переподключение сокета при обрыве сети (без обязательного действия пользователя);
- блокировка отправки сообщений, пока сокет не в статусе `connected`;
- синхронизация пропущенных каналов и сообщений через REST после успешного `reconnect`;
- индикация переподключения в форме сообщений и ручной Retry только при финальной ошибке соединения;
- toast-уведомления через `react-toastify` после успешного создания, переименования и удаления канала;
- toast-уведомления при ошибке загрузки данных чата и при невозможности восстановить соединение с сервером;
- обработка состояний загрузки, ошибок запроса и статусов socket-соединения (`idle`, `connecting`, `connected`, `disconnected`, `error`);
- обработка серверной ошибки регистрации при попытке создать уже существующего пользователя;
- глобальный `ErrorBoundary` и отправка клиентских ошибок в `Rollbar`;
- отправка в `Rollbar` не только ошибок рендера, но и неожиданных async/network ошибок из thunk-ов, авторизации и socket-соединения;
- автоматическая передача `environment`, `codeVersion` и данных текущего пользователя в события `Rollbar`;
- fallback-экран после критического сбоя с действиями `Обновить страницу` и `На главную`;
- скрытие чувствительных полей (`password`, `token`, `authorization`, `cookie` и др.) через `scrubFields`, без лишнего шума от ожидаемых бизнес-ошибок вроде неверного логина.

## FSD-архитектура

Проект был переработан под подход `Feature-Sliced Design (FSD)`.

Идея FSD в том, что код делится не случайно по папкам, а по уровням ответственности:

- на верхних уровнях лежит то, что собирает приложение целиком;
- ниже располагаются страницы и крупные блоки интерфейса;
- еще ниже находятся конкретные пользовательские действия и бизнес-сущности;
- в самом низу лежит общий переиспользуемый код.

Это упрощает масштабирование проекта: легче понимать, где должна жить новая логика, что можно переиспользовать, а что нельзя импортировать напрямую.

### Слои проекта

- `app` — верхний слой приложения. Здесь находится все, что нужно для запуска приложения целиком: роутер, Redux store, i18n-провайдер, общий shell, глобальные стили.
- `pages` — страницы маршрутов. Это компоненты, которые соответствуют URL и собирают нужные виджеты на экране.
- `widgets` — крупные составные блоки интерфейса. Они собирают несколько частей UI и могут использовать features/entities внутри себя.
- `features` — отдельные пользовательские действия. Например: вход в систему, регистрация, выход, выбор канала, отправка сообщения, создание/переименование/удаление канала.
- `entities` — бизнес-сущности приложения. Здесь хранится состояние, селекторы и доменная логика для конкретных сущностей, например `chat` и `session`.
- `shared` — общий переиспользуемый код, который не относится к одной конкретной бизнес-сущности: базовые UI-компоненты, конфиг маршрутов, словари переводов и вспомогательные вещи.

### Как это выглядит в этом проекте

- `app`
  - `src/app/providers/router` — маршрутизация приложения
  - `src/app/providers/store` — настройка Redux store
  - `src/app/providers/i18n` — инициализация `react-i18next`
  - `src/app/providers/rollbar` — конфигурация и подключение `Rollbar`
  - `src/app/ui/app-shell.jsx` — общий layout с navbar и глобальным `ToastContainer`
  - `src/app/styles` — глобальные стили
- `pages`
  - `src/pages/home` — домашняя страница
  - `src/pages/login` — страница входа
  - `src/pages/signup` — страница регистрации
  - `src/pages/not-found` — страница 404
- `widgets`
  - `src/widgets/chat` — экран чата как единый крупный UI-блок
  - `src/widgets/auth-layout` — layout для страницы авторизации
- `features`
  - `src/features/auth-by-username` — логика и форма входа
  - `src/features/sign-up-by-username` — логика и форма регистрации
  - `src/features/logout` — выход из системы
  - `src/features/select-channel` — выбор активного канала
  - `src/features/add-channel` — создание канала
  - `src/features/rename-channel` — переименование канала
  - `src/features/remove-channel` — удаление канала
  - `src/features/send-message` — отправка сообщения
- `entities`
  - `src/entities/session` — данные текущей сессии пользователя
  - `src/entities/chat` — состояние чата, селекторы, REST API, socket-клиент (`chat-socket.js`), хук `useChatSocket` и синхронизация после reconnect
- `shared`
  - `src/shared/ui/form-field` — переиспользуемое поле формы
  - `src/shared/config/i18n` — словари переводов `ru` и `en`
  - `src/shared/config/routes` — конфиг маршрутов

### Простое объяснение на примерах

- `HomePage` — это `page`, потому что это экран маршрута `/`.
- `Chat` — это `widget`, потому что он собирает целый экран чата из нескольких частей интерфейса.
- `send-message`, `add-channel`, `sign-up-by-username` и `logout` — это `features`, потому что это отдельные действия пользователя.
- `chat` и `session` — это `entities`, потому что это основные бизнес-сущности приложения.
- `FormField` и словари переводов — это `shared`, потому что это общий UI-код и конфигурация, которые не относятся к одной конкретной бизнес-сущности.

### Дополнительные правила структуры

- Для слайсов используются `Public API` через `index.js`.
- В проекте настроен алиас `@`, который указывает на `src`.
- Архитектурные ограничения проверяются через `ESLint` и FSD-правила.

## Локальный запуск

### 1. Установить зависимости

```bash
npm install
```

### 2. Запустить backend

Проект использует пакет [`@hexlet/chat-server`](https://www.npmjs.com/package/@hexlet/chat-server), который уже добавлен в зависимости.

```bash
npx start-server
```

По умолчанию backend будет доступен на `http://localhost:5001`.

### 3. Настроить переменные окружения

Для клиентского мониторинга ошибок локально создайте файл `.env.local`:

```bash
VITE_ROLLBAR_ACCESS_TOKEN='your_rollbar_post_client_item_token'
```

При деплое эту же переменную нужно задать в настройках хостинга. При необходимости можно дополнительно передать:

- `VITE_APP_ENV` — имя окружения вместо стандартного `development` / `production`;
- `VITE_GIT_SHA` — версия релиза или commit SHA для `codeVersion`.

### 4. Запустить frontend

```bash
npm run dev
```

Frontend будет доступен на `http://localhost:5002`.

В dev-режиме `Vite` проксирует:

- `/api` -> `http://localhost:5001`
- `/socket.io` -> `ws://localhost:5001`

## Как устроено приложение

- авторизация выполняется через `POST /api/v1/login`;
- регистрация выполняется через `POST /api/v1/signup`;
- сервер возвращает `token` и `username`;
- токен сохраняется в `localStorage` и используется в заголовке `Authorization: Bearer <token>`;
- после входа или регистрации приложение запрашивает каналы и сообщения;
- создание, переименование и удаление каналов выполняется через REST API;
- все тексты интерфейса вынесены в i18n-ресурсы;
- приложение стартует с локалью `ru`, а дополнительный словарь `en` подключен без автоматического определения языка;
- всплывающие уведомления показываются через `react-toastify`;
- за состояние авторизации отвечает `entities/session`;
- за состояние чата отвечает `entities/chat`;
- экран чата собирается через `widgets/chat`;
- новые сообщения и изменения каналов приходят через websocket-события `newMessage`, `newChannel`, `renameChannel`, `removeChannel`;
- отправка сообщений выполняется через `POST /api/v1/messages`, а `Socket.IO` используется для live-событий и контроля «онлайн»-состояния чата;
- сокет создаётся с `autoConnect: false` и подключается после загрузки данных чата; при обрыве клиент переподключается с бесконечным числом попыток и задержкой 1–5 с;
- при `reconnect` вызывается `refetchChatData`, чтобы догрузить пропущенные за время offline сообщения и каналы;
- `sendMessage` отклоняется с кодом `socket-offline`, если сокет не подключён (дублирует блокировку поля ввода в `MessageForm`);
- статус соединения хранится в `socketStatus` и отображается в композере: баннер «Переподключаемся…» при `connecting` / `disconnected`, кнопка «Повторить» — только при `error`;
- текст сообщений очищается от нецензурных слов через `leo-profanity` при отправке, загрузке истории и получении новых сообщений;
- при создании и переименовании канала имя автоматически очищается от нецензурных слов перед сохранением;
- точка входа приложения обёрнута в `Rollbar Provider` и `ErrorBoundary`, поэтому ошибки React-дерева автоматически отправляются в `Rollbar`;
- в события `Rollbar` добавляются данные текущего пользователя; сейчас используется `username`, а логика уже готова к переходу на отдельный `userId`;
- неожиданные ошибки запросов и socket-соединения логируются в `Rollbar` с дополнительным контекстом операции;
- ожидаемые бизнес-ошибки, например неверный логин или попытка зарегистрировать уже существующего пользователя, не засоряют мониторинг как технические сбои;
- чувствительные поля исключаются из отправки через `scrubFields`;
- при критическом сбое `ErrorBoundary` показывает fallback-экран с кнопками перезагрузки страницы и перехода на главную;
- успешные действия с каналами подтверждаются toast-уведомлениями; toast при финальной ошибке socket-соединения показывается только если автопереподключение не удалось;
- страница регистрации использует отдельную форму с валидацией `username`, `password` и `confirmPassword`.
